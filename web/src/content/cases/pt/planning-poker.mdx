## Contexto

Planning poker precisa de uma sala compartilhada, votos simultâneos e revelação
instantânea — na prática: WebSockets, estado compartilhado e uma UI que nunca parece
desatualizada.

Eu queria mais do que uma demo. Este projeto é o ciclo completo que uso para validar
decisões de plataforma de ponta a ponta: escrever o serviço, containerizar, publicar
imagens, fazer deploy com GitOps e observar sob tráfego real antes que qualquer outra
coisa dependa dele.

## Como funciona

- **Salas com papéis.** Cada sala tem um dono, participantes e espectadores; os votos
  ficam privados até o dono revelar.
- **Tempo real por padrão.** A API em Go mantém um WebSocket por cliente. O estado da
  sala vive em um hub; cada voto e revelação é propagado via Redis pub/sub.
- **Instâncias stateless.** Nenhuma instância guarda a única cópia de nada. Qualquer
  réplica pode atender qualquer usuário — o que deixa o deploy de produção sem
  surpresas: três réplicas, sem sticky sessions.

## Decisões e trade-offs

- **Redis pub/sub em vez de broadcast em memória.** Em memória é mais simples e
  funcionaria com uma réplica, mas fixa um ponto único de falha. O pub/sub custa um hop
  a mais e compra escala horizontal e rolling restarts que não derrubam salas.
- **Backend em camadas (domain → application → infra).** As regras da sala são Go puro;
  WebSocket, Redis e HTTP ficam atrás de fronteiras. Os testes rodam contra a mesma
  fiação usada em produção, porque o container monta o grafo uma única vez.
- **A pirâmide de testes se mantém honesta.** Testes unitários ao lado do código;
  integração sobe o app completo via `httptest` contra um Redis real; Playwright cobre
  os fluxos críticos — e roda dentro do Docker, então uma lib faltando no host nunca
  bloqueia a CI.
- **GitOps com uma aplicação por ambiente.** Staging e produção são aplicações ArgoCD
  separadas apontando para o mesmo Helm chart com values diferentes. Promover é mudar
  values, não rodar `kubectl` na mão.
- **Observabilidade desde o primeiro dia.** Traces vão para o Tempo, métricas são
  coletadas pelo gateway do OTel Collector e enviadas ao Prometheus, logs vão para o
  Loki. É também um app de WebSocket o que finalmente me fez levar a sério as métricas
  por conexão e o comportamento de reconexão.

## Resultados e próximos passos

O app roda em produção no homelab e é usado por times reais em sessões, com staging
publicado a partir do mesmo chart para experimentos seguros.

Próximos passos que já acompanho:

- Migrar `active_users` / `active_rooms` de contadores para gauges, para números exatos
  (é o que a página `/lab` do portfólio lê — veja o ADR 0003 no repositório do
  portfólio).
- Melhorar a reconexão quando um notebook dorme no meio da sessão.
- Publicar um teste de carga mostrando até onde três réplicas aguentam antes de o Redis
  virar gargalo.
