## Context

Agentic coding tools consolidated faster than the ways to evaluate them. Every week
brings a new model to try, and "this one feels better" is not a criterion I can defend
in a technical discussion — especially when the cost per task differs by an order of
magnitude.

I wanted two things: to run several agents in parallel without them stepping on each
other, and to compare models on the same tasks with actual numbers.

## What I built

- **A local orchestrator.** It dispatches tasks to different agent CLIs (OpenCode,
  Codex, Claude Code) behind a common adapter, each one running in its own git
  worktree — the isolation primitive that makes parallel work safe and reviewable.
- **A benchmark harness.** A suite of real tasks taken from my own repositories,
  executed by each model/agent combination, with results recorded: task completion,
  quality against a checklist, token cost and wall-clock time.
- **Reusable GitHub Actions.** The same idea ported to CI: a pull-request comment like
  `/oc` or `/review-oc` triggers an agent review of the change, reused across
  repositories (it runs in the planning-poker repo today).

## Decisions and trade-offs

- **One adapter per tool.** Each agent CLI sits behind a thin adapter, so trying a new
  tool is a configuration change. The trade-off is dealing with
  least-common-denominator features — but the harness measures the rest.
- **Benchmarks from my own repositories.** My repositories have real constraints:
  conventions, tests, a review process. A model that solves puzzle tasks but ignores
  `AGENTS.md` is not useful to me.
- **Cost is a first-class metric.** Tokens and latency are collected next to quality,
  because "best" means little without the price tag sitting next to it.
- **Keep it boring and scriptable.** Everything runs on the command line and writes
  structured logs. The harness stays small on purpose.

## Results and next steps

The orchestrator runs reliably every day, and the benchmark harness is what I use to
decide which model handles which class of work — refactors, small fixes, review
comments.

Next steps:

- Publish benchmark results periodically, with the task suite in the repository.
- Extend the harness to score review quality as well as task completion.
