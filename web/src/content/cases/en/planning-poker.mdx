## Context

Planning poker needs a shared room, simultaneous votes and instant reveal — which is
another way of saying: WebSockets, shared state and a UI that never feels stale.

I wanted more than a demo. This project is the round trip I use to validate platform
decisions end to end: write the service, containerize it, publish images, deploy with
GitOps, and then watch it under real traffic before anything else depends on it.

## How it works

- **Rooms with roles.** Every room has an owner, participants and spectators; votes are
  private until the owner reveals them.
- **Real-time by default.** The Go API keeps a WebSocket per client. The room state
  lives in a hub; every vote and reveal is broadcast through Redis pub/sub.
- **Stateless instances.** No instance holds the only copy of anything. Any replica can
  serve any user, which is what makes the production deployment boring — in the good
  way (three replicas, no sticky sessions).

## Decisions and trade-offs

- **Redis pub/sub instead of in-memory broadcast.** In-memory is simpler and would work
  on a single replica, but it locks in a single point of failure. Pub/sub costs one
  extra hop and buys horizontal scale and rolling restarts that don't drop rooms.
- **Layered backend (domain → application → infra).** The room rules are pure Go; the
  WebSocket, Redis and HTTP details live behind boundaries. Tests run against the same
  wiring used in production because the container builds the graph once.
- **The testing pyramid stays honest.** Unit tests sit next to the code; integration
  tests spin up the full app over `httptest` against a real Redis; Playwright covers the
  critical flows — and runs inside Docker, so a missing host library can never block CI.
- **GitOps with per-environment applications.** Staging and production are separate
  ArgoCD applications pointing at the same Helm chart with different values. Promotion
  is a values change, not a manual `kubectl`.
- **Observability from day one.** Traces go to Tempo, metrics are scraped through the
  OTel Collector gateway into Prometheus, logs go to Loki. The interesting part is not
  the stack — it is that a WebSocket app finally made me care about per-connection
  metrics and reconnect behaviour.

## Results and next steps

The app runs in production on the homelab and is used by real teams for sessions, with
staging deployed from the same chart for safe experiments.

Next steps I already track:

- Move `active_users` / `active_rooms` from counters to gauges so the numbers are exact
  (this is what the portfolio's `/lab` page reads — see ADR 0003 in the portfolio
  repository).
- Improve the reconnection experience when a laptop sleeps mid-session.
- Publish a load test showing how far three replicas go before Redis becomes the
  bottleneck.
